# ADR-003: 自研 BM25 检索，pgvector 留作可选扩展

状态：已采纳 | 日期：2026-10-28

## 背景

知识库检索需要排序能力。选项：引入向量库（Milvus/Qdrant/pgvector）、全文搜索引擎（Elasticsearch）、或自研轻量检索。

## 决策

自研 Okapi BM25（k1=1.5, b=0.75）内存倒排（`knowledge_base/bm25.py`），配中英混合分词（英文按词、中文单字+bigram）。`Retriever` 协议是检索能力的唯一抽象，pgvector 语义检索作为可选扩展实现同一协议即可替换。

## 理由

- **规模匹配**：内置语料数百条，BM25 内存倒排毫秒级返回；为这个量级引入向量库是部署成本而非能力收益；
- **离线硬约束**：嵌入向量需要模型调用，离线（无 Key）模式下不可用；BM25 纯 CPU 零依赖，测试确定性可复现；
- **分词选 bigram 而非单字**：中文单字区分度太低（"向量库"会命中一切含"量"的文档）；无 jieba 依赖的前提下 bigram 保留大部分区分度；
- **中文 bigram + 英文词的混合策略**在演示语料上的命中率足够支撑主流程（评测断言可证）。

## 后果

+ 零依赖、零网络、毫秒级、确定性；
− 无语义泛化（"embedding 存储"检索不到只说"向量索引"的文档）——领域内问题的 query 由 Planner 用标准术语构造，实际影响有限；真正需要语义召回时实现 `Retriever` 协议接 pgvector，上层零改动。
